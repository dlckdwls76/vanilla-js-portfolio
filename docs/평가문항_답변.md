# 평가문항 답변

각 문항의 코드 링크를 클릭하면 GitHub의 해당 코드 줄이 열립니다. 링크는 설명과 줄 번호가 일치하도록 코드 버전 `6291c09`에 고정했습니다.

## 질문 1. GitHub API에서 데이터를 불러와 화면에 표시되고, 로딩/에러/빈 상태가 구분되는가?

### 이 질문은 무엇을 묻는가?

“GitHub에서 내 프로젝트 목록을 가져와 보여주고, 가져오는 중인지, 실패했는지, 보여줄 내용이 없는지를 사용자에게 알려주는가?”를 묻는 질문입니다.

### GitHub API는 무엇인가?

GitHub API는 **프로그램이 GitHub에 정보를 요청하고 받아올 수 있는 통로**입니다.

이 포트폴리오는 GitHub에 “내 공개 저장소 목록을 알려주세요”라고 요청합니다. GitHub는 저장소 이름, 설명, 사용 언어 같은 정보를 데이터로 보내줍니다. JavaScript는 그 데이터를 이용해 화면에 프로젝트 카드를 만듭니다.

```text
포트폴리오에서 목록 요청
→ GitHub가 저장소 정보 전달
→ JavaScript가 정보를 카드로 변환
→ 프로젝트 영역에 표시
```

GitHub 화면을 사진처럼 가져오는 것이 아니라, **정보를 받아서 내 웹페이지의 모양으로 보여주는 것**입니다. 현재 코드는 최근 업데이트된 공개 저장소를 최대 12개 요청합니다.

### 내 GitHub에서 API는 어디에 있는가?

**API는 내 저장소 안에 들어 있는 파일이 아니라, GitHub가 운영하는 서버에 정보를 요청하는 주소입니다.** 내 프로젝트에는 그 주소를 호출하는 코드가 있습니다.

이 프로젝트에서 사용하는 주소는 다음과 같습니다.

[내 공개 저장소 목록을 요청하는 GitHub API 열기](https://api.github.com/users/dlckdwls76/repos?sort=updated&direction=desc&per_page=12)

| 주소의 부분 | 뜻 |
| --- | --- |
| `api.github.com` | GitHub의 API 서버 |
| `/users/dlckdwls76/repos` | `dlckdwls76` 사용자의 공개 저장소 목록 요청 |
| `sort=updated&direction=desc` | 최근 업데이트된 순서로 정렬 |
| `per_page=12` | 한 번에 최대 12개 요청 |

내 저장소에서 이 주소를 사용하는 위치는 **`js/main.js` 173~174줄**입니다.

```js
const url = `https://api.github.com/users/${SETTINGS.githubUsername}/repos?sort=updated&direction=desc&per_page=12`;
const response = await fetch(url, { signal: controller.signal });
```

- 첫 줄은 데이터를 요청할 주소를 만듭니다. `SETTINGS.githubUsername`에는 6줄에서 `"dlckdwls76"`를 넣었습니다.
- 두 번째 줄의 `fetch(url, ...)`이 그 주소로 실제 요청을 보냅니다.
- GitHub는 정상 요청에 저장소 정보를 JSON이라는 데이터 형식으로 응답하고, 포트폴리오 코드는 그 정보를 카드로 보여줍니다.

이 프로젝트는 GitHub가 제공하는 API를 JavaScript 코드에서 호출해 사용합니다.

### 어떤 상태를 구분하는가?

| 상태 | 쉽게 설명하면 | 이 프로젝트에서 보여주는 화면 |
| --- | --- | --- |
| 로딩 (`loading`) | “요청했어요. 아직 기다리는 중이에요.” | `프로젝트를 불러오는 중...` |
| 성공 (`success`) | “프로젝트 정보를 받았어요.” | 저장소 이름·설명 등이 담긴 프로젝트 카드 |
| 에러 (`error`) | “정보를 가져오거나 처리하는 데 실패했어요.” | 오류 안내와 `다시 시도` 버튼 |
| 빈 상태 (`empty`) | “정상적으로 확인했지만 프로젝트가 없어요.” | `표시할 프로젝트가 없습니다.` |

**에러와 빈 상태는 다릅니다.**

- **에러:** 연결 문제나 실패 응답 등으로 목록을 정상적으로 가져오지 못했습니다.
- **빈 상태:** 요청과 데이터 처리는 성공했지만, 받은 목록에 프로젝트가 0개입니다.

예를 들어 “조회 자체가 실패한 경우”와 “조회는 됐지만 검색 결과가 0건인 경우”의 차이입니다.

이렇게 안내해야 사용자가 빈 화면을 보고 **기다려야 하는지, 다시 시도해야 하는지, 원래 데이터가 없는지** 판단할 수 있습니다.

### 내 코드에서는 어떻게 이어지는가?

역할은 다음 세 가지로 나뉩니다.

| 코드 | 역할 | 쉬운 표현 |
| --- | --- | --- |
| `loadProjects()` | GitHub에 요청하고 결과를 처리합니다. | 정보를 가져오는 함수 |
| `state.projects.status` | 현재 상황을 저장합니다. | 지금 어떤 상황인지 적어 두는 값 |
| `renderProjects()` | 상태에 맞게 카드나 안내 문구를 표시합니다. | 상황을 화면에 보여주는 함수 |

처리 순서는 다음과 같습니다.

1. **요청 시작:** 상태를 `loading`으로 바꾸고 로딩 안내를 표시합니다.
2. **정보 요청:** `fetch()`로 GitHub API에 요청합니다.
3. **결과 구분:** 정상 응답의 목록에 데이터가 있으면 `success`, 없으면 `empty`로 바꿉니다. 요청이나 처리 중 오류가 발생하면 `error`로 바꿉니다.
4. **화면 갱신:** `renderProjects()`가 현재 상태를 읽고 알맞은 화면을 표시합니다.

실제 코드에서 성공과 빈 상태를 구분하는 줄은 다음과 같습니다.

```js
state.projects.status = projects.length > 0 ? "success" : "empty";
```

- `projects.length`: 받아 온 프로젝트의 개수입니다.
- `> 0`: 프로젝트가 하나 이상인지 확인합니다.
- `? "success" : "empty"`: 하나 이상이면 성공, 0개이면 빈 상태를 선택합니다.

오류가 발생하면 `catch`에서 다음과 같이 기록합니다.

```js
state.projects.status = "error";
```

화면에 표시할 안내 문구는 `renderProjects()`에 정의되어 있습니다. 아래는 해당 부분의 발췌입니다.

```js
loading: "프로젝트를 불러오는 중...",
empty: "표시할 프로젝트가 없습니다.",
error: `프로젝트를 불러올 수 없습니다. ${error}`,
```

오류 상태일 때만 재시도 버튼을 보여주는 코드도 있습니다.

```js
elements.retryButton.hidden = status !== "error";
```

`hidden`이 `true`이면 숨깁니다. 따라서 오류 상태에서는 버튼을 보여주고, 나머지 상태에서는 숨깁니다.

이 프로젝트에는 GitHub API에서 공개 저장소 목록을 가져와 프로젝트 카드로 보여주는 코드가 구현되어 있습니다. 정보를 기다리는 동안에는 ‘불러오는 중’이라는 안내를 표시합니다. 정상적으로 받으면 카드를 보여주고, 실패하면 오류 안내와 다시 시도 버튼을 보여줍니다. 요청은 성공했지만 프로젝트가 0개이면 ‘표시할 프로젝트가 없습니다’라고 안내합니다. 이렇게 구분해서 사용자가 현재 상황을 알 수 있도록 했습니다.

`loadProjects()`가 정보를 가져오고, `state.projects.status`에 현재 상황을 저장합니다. 그리고 `renderProjects()`가 그 상태를 읽어서 화면을 바꿉니다.

## 질문 2. HTML, CSS, JavaScript가 각각의 파일로 분리되어 있고, 분리한 이유와 각 파일의 역할을 구분하여 답변할 수 있는가?

### 이 질문은 무엇을 묻는가?

“웹페이지의 구조, 디자인, 동작을 각각 어느 파일에 작성했고, 왜 나누어 관리했는지 설명할 수 있는가?”를 묻는 질문입니다.

### 내 프로젝트에서는 어디에 나뉘어 있는가?

```text
vanilla-js-portfolio/
├── index.html
├── css/
│   └── style.css
└── js/
    └── main.js
```

| 기술 | 내 파일 | 역할 | 쉽게 기억하는 말 |
| --- | --- | --- | --- |
| HTML | `index.html` | 제목, 문단, 버튼, 입력창 등 내용과 구조를 만듭니다. | 무엇을 보여줄까? |
| CSS | `css/style.css` | 색상, 글꼴, 간격, 크기와 화면 배치를 정합니다. | 어떻게 보이게 할까? |
| JavaScript | `js/main.js` | 클릭에 반응하고, 데이터를 가져오며, 입력값을 검사합니다. | 어떤 동작을 할까? |

세 파일은 하나의 웹페이지를 만들기 위해 함께 사용됩니다.

### 다크 모드 버튼 하나로 이해하기

**HTML은 버튼을 만듭니다.** `index.html` 18줄입니다.

```html
<button class="icon-button" id="theme-toggle" type="button" aria-pressed="false">다크 모드</button>
```

이 코드는 ‘다크 모드’라는 글자가 적힌 버튼을 만듭니다. `class="icon-button"`은 CSS 스타일과 연결하고, `id="theme-toggle"`은 JavaScript가 이 버튼을 찾는 데 사용합니다.

**CSS는 버튼의 모양을 정합니다.** `css/style.css` 71줄의 일부를 추리면 다음과 같습니다.

```css
.icon-button {
  min-height: 44px;
  padding: 0.4rem 0.8rem;
  color: var(--text);
  border: 1px solid var(--line);
  border-radius: 0.4rem;
}
```

버튼의 최소 높이, 안쪽 여백, 글자색, 테두리와 둥근 모서리를 정합니다. `.icon-button`은 HTML에서 해당 클래스를 가진 요소를 선택한다는 뜻입니다.

**JavaScript는 클릭했을 때 할 일을 연결합니다.** `js/main.js` 237줄입니다.

```js
elements.themeButton.addEventListener("click", toggleTheme);
```

`elements.themeButton`은 코드에서 찾아 둔 테마 버튼입니다. 사용자가 클릭하면 `toggleTheme()`을 실행합니다. 이 함수는 테마 상태를 바꾸고, `renderTheme()`을 호출해 화면에 반영합니다.

```text
HTML: 다크 모드 버튼을 만든다.
CSS: 버튼의 크기·색상·테두리를 정한다.
JavaScript: 버튼을 누르면 테마가 바뀌도록 처리한다.
```

### 왜 파일을 나누었는가?

**수정하려는 내용에 따라 담당 파일을 쉽게 찾고 관리하기 위해서입니다.**

| 수정하고 싶은 내용 | 먼저 살펴볼 파일 |
| --- | --- |
| 소개 문장이나 처음 표시할 버튼 문구 | `index.html` |
| 버튼의 크기·색상·여백 | `css/style.css` |
| 버튼을 눌렀을 때 실행할 동작 | `js/main.js` |

나누어 관리하면 다음과 같은 이점이 있습니다.

1. **찾기 쉽습니다.** 구조·디자인·동작 중 무엇을 수정할지에 따라 살펴볼 위치가 분명합니다.
2. **읽고 고치기 쉽습니다.** 한 파일에 모든 종류의 코드가 섞여 있는 것보다 각 역할에 집중할 수 있습니다.
3. **함께 작업하기 쉽습니다.** 동료끼리 구조, 디자인, 기능을 나누어 담당하기 좋습니다.
4. **재사용하기 쉽습니다.** 같은 스타일이나 기능이 필요한 다른 페이지에서 CSS와 JavaScript 파일을 연결해 사용할 수 있습니다.

한 HTML 파일 안에 CSS와 JavaScript를 작성하는 것도 가능합니다. 파일 분리는 실행을 위한 필수 조건이 아니라, 코드가 늘어났을 때도 역할을 구분해 관리하기 위한 선택입니다. 파일을 나누어도 클래스 이름이나 요소 ID를 바꿀 때는 서로 연결된 코드를 함께 확인해야 합니다.

### 나눈 파일은 어떻게 연결하는가?

`index.html` 9~10줄에서 두 파일을 연결합니다.

```html
<link rel="stylesheet" href="css/style.css">
<script src="js/main.js" defer></script>
```

- `link`: 지정한 CSS 파일을 읽어 화면에 스타일을 적용합니다.
- `script`: 지정한 JavaScript 파일을 읽어 실행합니다.
- `defer`: HTML을 해석하는 동안 JavaScript 파일을 내려받고, HTML 해석이 끝난 뒤 실행하게 합니다. 버튼 등의 요소가 만들어진 다음 코드가 그 요소를 찾을 수 있습니다.

HTML은 `index.html`, CSS는 `css/style.css`, JavaScript는 `js/main.js`로 분리했습니다. HTML은 제목과 버튼 같은 내용과 구조를 만들고, CSS는 색상과 배치를 정하며, JavaScript는 클릭이나 입력에 반응하는 동작을 처리합니다. 예를 들어 HTML로 다크 모드 버튼을 만들고, CSS로 버튼을 꾸미고, JavaScript로 클릭했을 때 테마가 바뀌게 했습니다. 이렇게 역할별로 나누면 수정할 위치를 찾기 쉽고, 코드를 읽거나 동료와 나누어 작업하기 편합니다.

## 질문 3. header, nav, main, section, footer 등 시맨틱 태그를 사용했고, 어떤 기준으로 태그를 선택했는지 설명할 수 있는가?

### 이 질문은 무엇을 묻는가?

“페이지를 구성하는 각 영역에 알맞은 의미의 HTML 태그를 사용했고, 왜 그 태그를 골랐는지 설명할 수 있는가?”를 묻는 질문입니다.

### 시맨틱 태그는 무엇인가?

시맨틱(semantic)은 ‘의미가 있는’이라는 뜻입니다. **시맨틱 태그는 그 안의 내용이 어떤 역할인지 알려주는 HTML 태그**입니다.

예를 들어 `nav`는 주요 이동 메뉴라는 의미이고, `main`은 페이지의 핵심 내용이라는 의미입니다. 책에서 목차와 본문을 구분하는 것처럼, 웹페이지에서도 영역마다 역할을 구분해 주는 것입니다.

### 내 페이지에서는 어떻게 사용했는가?

| 태그 | 태그의 의미 | 내 포트폴리오에서 사용한 곳 | 선택한 이유 |
| --- | --- | --- | --- |
| `header` | 페이지나 구역의 도입부 | 로고와 메뉴가 있는 페이지 상단 | 사이트를 소개하고 탐색을 시작하는 영역이기 때문입니다. |
| `nav` | 주요 탐색 링크를 모은 영역 | 소개·기술·프로젝트·연락 메뉴 | 사용자가 원하는 구역으로 이동하는 메뉴이기 때문입니다. |
| `main` | 페이지의 핵심 내용 | 첫 소개부터 연락 폼까지 | 방문자에게 전달하려는 중심 내용이기 때문입니다. |
| `section` | 하나의 주제로 묶인 구역 | 첫 소개, 자기소개, 기술, 프로젝트, 연락 | 각 영역이 서로 다른 주제를 갖고 있기 때문입니다. |
| `footer` | 페이지나 구역의 마무리 정보 | 저작권 문구와 GitHub 링크 | 페이지의 마무리 정보를 제공하기 때문입니다. |

구조를 이해하기 쉽게 내용과 속성을 생략하면 다음과 같습니다.

```html
<header>
  <nav>로고와 주요 이동 메뉴</nav>
</header>

<main>
  <section>첫 소개</section>
  <section>자기소개</section>
  <section>배우는 기술</section>
  <section>프로젝트 목록</section>
  <section>연락 안내와 입력 폼</section>
</main>

<footer>저작권 문구와 GitHub 링크</footer>
```

`header` 안에 `nav`가 있고, `main` 안에 여러 `section`이 있습니다. 상단·본문·하단으로 큰 역할을 나누고, 본문 안에서는 주제별로 구역을 나눈 것입니다.

### 태그를 고르는 기준은 무엇인가?

**화면에서의 위치나 모양보다, 그 내용이 맡는 역할을 기준으로 고릅니다.**

- 페이지나 구역을 소개하는 내용이면 `header`를 사용합니다.
- 주요 이동 링크를 모아 놓은 메뉴이면 `nav`를 사용합니다.
- 페이지의 핵심 내용이면 `main`을 사용합니다.
- 제목을 붙여 설명할 수 있는 하나의 주제이면 `section`을 사용합니다.
- 페이지나 구역의 마무리 정보이면 `footer`를 사용합니다.
- 특별한 의미 없이 배치나 스타일을 위해 묶는다면 `div`를 사용합니다.

예를 들어 프로젝트 목록은 ‘내가 만든 프로젝트’라는 주제가 있으므로 `section`을 사용했습니다. 반면 두 버튼을 가로로 놓기 위한 묶음은 `div class="button-row"`로 작성했습니다.

또한 링크가 있다고 전부 `nav`로 감싸는 것은 아닙니다. 이 프로젝트에서는 주요 이동 메뉴에 `nav`를 사용했고, 하단의 GitHub 링크는 `footer` 안에 두었습니다.

### 모두 div로 작성하면 안 되는가?

`div`와 CSS만으로도 비슷한 모양을 만들 수 있습니다. 다만 `div` 자체는 그 영역이 메뉴인지, 본문인지, 마무리 정보인지 알려주지 않습니다.

시맨틱 태그를 사용하면 다음과 같은 이점이 있습니다.

1. **코드를 읽기 쉽습니다.** 태그 이름을 보고 해당 영역의 역할을 파악할 수 있습니다.
2. **접근성에 도움이 됩니다.** 화면 낭독기 같은 보조기기가 탐색 영역과 본문 등 문서의 주요 영역을 구분하는 데 활용할 수 있습니다.
3. **구조를 유지하기 쉽습니다.** 다른 사람이 수정할 때도 어떤 내용이 어느 영역에 속하는지 이해하기 좋습니다.

태그는 의미를 정하고, 실제 색상·위치·배치는 CSS가 정합니다. 예를 들어 `header`라고 작성했다고 자동으로 화면 위에 고정되는 것은 아닙니다. 이 프로젝트에서는 `.site-header`의 `position: sticky`가 스크롤할 때 상단에 붙는 동작을 만듭니다.

내용의 의미와 역할에 맞춰 시맨틱 태그를 사용했습니다. 로고와 메뉴가 있는 도입부는 `header`, 주요 이동 메뉴는 `nav`, 페이지의 핵심 내용은 `main`으로 작성했습니다. 본문 안에서는 소개·기술·프로젝트처럼 주제가 나뉘는 부분을 `section`으로 묶고, 저작권과 마무리 링크는 `footer`에 넣었습니다. 단순히 배치를 위해 묶는 부분에는 `div`를 사용했습니다. 이렇게 작성하면 코드만 보고도 영역의 역할을 이해하기 쉽고, 보조기기가 문서 구조를 파악하는 데도 도움이 됩니다.

## 질문 4. CSS 변수(:root)로 색상, 폰트 등을 정의했고, 변수로 관리하면 어떤 이점이 있는지 구체적으로 답변할 수 있는가?

### 이 질문은 무엇을 묻는가?

“반복해서 사용하는 색상과 글꼴 등의 디자인 값에 이름을 붙여 관리했고, 이렇게 관리하면 무엇이 편리한지 설명할 수 있는가?”를 묻는 질문입니다.

### CSS 변수와 :root는 무엇인가?

CSS 변수는 **디자인 값에 이름을 붙여 놓고, 필요한 곳에서 그 이름으로 가져다 쓰는 기능**입니다. 정식 이름은 사용자 지정 속성(custom property)입니다.

예를 들어 흰색을 뜻하는 `#ffffff`에 `--bg`라는 이름을 붙이고, 배경색이 필요한 곳에서 `var(--bg)`로 사용합니다.

`:root`는 변수 이름이 아니라 **문서의 최상위 요소를 선택하는 CSS 선택자**입니다. HTML 문서에서는 `<html>` 요소를 가리킵니다. 이곳에 공통 변수를 정의하면 하위 요소로 상속되어 페이지 여러 곳에서 사용할 수 있습니다.

```css
:root {
  --bg: #ffffff;
}

body {
  background: var(--bg);
}
```

| 코드 | 뜻 |
| --- | --- |
| `:root` | HTML 문서의 최상위 요소를 선택합니다. |
| `--bg` | 배경색에 사용할 변수 이름입니다. CSS 변수 이름은 `--`로 시작합니다. |
| `#ffffff` | 변수에 넣은 값으로, 흰색을 뜻합니다. |
| `var(--bg)` | 현재 적용되는 `--bg` 값을 가져와 사용합니다. |

쉽게 말하면 “배경색이라는 이름표를 붙여 두고, 필요한 곳에서 그 값을 꺼내 쓴다”는 뜻입니다.

### 내 프로젝트에서는 무엇을 변수로 정의했는가?

`css/style.css` 2~17줄에서 공통 디자인 값을 정의했습니다. 일부를 추리면 다음과 같습니다.

```css
:root {
  --bg: #ffffff;
  --text: #172d26;
  --accent: #235d47;
  --font: "Malgun Gothic", "Apple SD Gothic Neo", system-ui, sans-serif;
  --radius: 0.8rem;
}
```

| 변수 | 용도 |
| --- | --- |
| `--bg` | 기본 배경색 |
| `--text` | 기본 글자색 |
| `--accent` | 버튼이나 링크 등에 사용하는 강조색 |
| `--font` | 사용할 글꼴 목록 |
| `--radius` | 여러 요소에서 공유하는 둥근 모서리 크기 |

정의한 색상과 글꼴은 `body`에서 다음처럼 사용합니다. 실제 35줄의 관련 속성을 추린 코드입니다.

```css
body {
  background: var(--bg);
  color: var(--text);
  font-family: var(--font);
}
```

`--font`에는 글꼴을 여러 개 적어 두었습니다. 브라우저는 앞쪽 글꼴부터 사용 가능한 글꼴을 선택하므로, 사용자의 기기에 특정 글꼴이 없어도 다음 글꼴을 사용할 수 있습니다.

### 변수로 관리하면 무엇이 좋은가?

**1. 한곳을 수정해 여러 곳에 반영할 수 있습니다.**

현재 `.text-link`의 글자색과 `.primary` 버튼의 배경색은 모두 `--accent`를 사용합니다.

```css
.text-link {
  color: var(--accent);
}

.primary {
  background: var(--accent);
}
```

라이트 모드의 강조색을 바꾸려면 `:root`의 `--accent` 값을 수정하면 됩니다. 그러면 같은 변수를 사용하는 링크와 버튼에 함께 반영됩니다. 각 요소의 색상 코드를 찾아서 따로 바꾸는 작업이 줄어듭니다.

**2. 디자인을 일관되게 유지하기 쉽습니다.**

같은 강조색을 써야 하는 요소들이 하나의 값을 공유합니다. 일부 요소만 수정해서 색상이 달라지는 실수를 줄일 수 있습니다.

**3. 코드의 의미를 이해하기 쉽습니다.**

`#235d47`이라는 색상 코드만 있으면 용도를 바로 알기 어렵지만, `--accent`라고 적혀 있으면 강조색에 사용한다는 의도를 파악하기 쉽습니다.

**4. 다크 모드를 만들기 편합니다.**

다크 모드에서 사용할 변수값을 따로 정의하면, 각 요소의 스타일을 전부 다시 작성할 필요가 줄어듭니다.

```css
[data-theme="dark"] {
  --bg: #121c18;
  --text: #edf3ed;
  --accent: #c6ed84;
}
```

JavaScript가 `<html>`의 `data-theme`을 `dark`로 바꾸면 위 규칙이 적용됩니다. `body`의 `background: var(--bg)` 코드는 그대로여도, 참조하는 배경색이 어두운 값으로 바뀝니다.

```text
라이트 모드: --bg가 #ffffff → 흰색 배경
다크 모드:  --bg가 #121c18 → 어두운 배경
```

다크 모드에서 별도로 정의한 값은 해당 규칙에서 수정해야 합니다. 또한 변수값을 바꿨을 때 영향을 받는 곳은 그 변수를 사용하는 요소입니다. 색상 코드를 직접 적어 둔 부분까지 자동으로 바뀌는 것은 아닙니다.

`css/style.css`의 `:root`에 배경색, 글자색, 강조색과 글꼴 등을 CSS 변수로 정의했습니다. 필요한 요소에서는 `var()`로 그 값을 가져다 씁니다. 예를 들어 링크와 버튼이 같은 강조색 변수를 사용하므로, 변수 한 곳을 수정하면 함께 바뀝니다. 이렇게 하면 중복 수정을 줄이고 디자인을 일관되게 유지할 수 있습니다. 다크 모드에서도 각 요소를 일일이 수정하지 않고 테마에 맞는 변수값을 적용해 색상을 바꾸도록 했습니다.

## 질문 5. onclick 인라인 속성 대신 addEventListener를 사용한 이유를 두 방식의 차이를 비교하여 제시할 수 있는가?

## 질문 7. async/await와 try/catch를 사용하여 API 호출 성공과 실패를 어떻게 분기 처리했는지 코드 흐름을 따라 답변할 수 있는가?

- `catch`: 그 과정에서 발생한 오류를 받아 처리합니다.
- `finally`: 성공·실패 처리 후 타이머를 정리하고 화면을 갱신합니다.

## 질문 11. 반응형 디자인에서 "모바일 퍼스트"로 작성한 이유를 이야기할 수 있는가?

**모바일 퍼스트는 작은 화면의 배치를 기본으로 만들고, 화면이 넓어지면 필요한 스타일을 추가하는 방식입니다.**
